# ResKonnect Promotion Studio & Notification Controls — 24 Nov 2026

## Goal and canonical ownership
Use the existing governed `site_announcements` to promote a single campaign/residence with an editable square image, center popup or corner floating card. Keep existing `hero_slides` for 16:9 hero artwork, existing Promotional Banners for category rails, and Visual Studio for Spotlight/Trusted/Top 3. No duplicate unmanaged popup table.

## Admin: upload the TWO approved posters
1. **Wide slider, 16:9:** `/admin/media?tab=slides` → find the inactive draft **2027 Single Room Requests**, image currently a placeholder; upload the existing generated wide artwork; confirm button label `REQUEST NOW` and link `/single-room-waiting-list`; preview; only then activate. The expired **TUT 2027 Applications Closing Soon** slide was explicitly disabled on 24 Nov because it still advertised a 30 September 2026 deadline. It remains in media history.
2. **Square pop-up, 1:1:** `/admin/media?tab=campaigns` → **Single-room campaign**, upload the existing square artwork (JPG/PNG/WebP ≤6 MB), select **Poster-only**, choose **Center pop-up** or **Floating ad**, move the **width** slider (280–760 px), set **CTA** `/single-room-waiting-list`, audience, schedule, 24h/session/campaign frequency. The campaign defaults **disabled** until explicitly enabled. Preview the actual student form before activation.
3. **Promoting a specific paying/partner residence:** same Promotion Studio → **New promotion** → search/select a published residence. The editor fills its canonical detail link and existing cover if available. Upload branded campaign artwork, select width/surface and schedule. Paid/sponsored claims still require verified agreements and appropriate sponsorship disclosures; selecting a residence in a campaign does **not** classify it as paid or guarantee an available room. Wide hero images and other banners stay in their canonical tabs.

### UX safeguards
- No poster is automatically activated; public visitors see only currently enabled, in-schedule, audience-matching campaigns.
- Poster-only preserves full 1:1 image without cropping, with a real click-through CTA beneath.
- Mobile popups are bounded by viewport height and available width; 280–760px is desktop maximum, not a fixed phone size.
- Centered or corner placement. Cross-browser/session suppression is best effort, not device-global tracking. Visitors can close default campaigns.
- Existing RG11 risk-sensitive approval guard/RLS remains enforced. Media uploads use existing admin-images storage bucket and its admin-only write policy.
- Campaign creation and the title/CTA do not notify individual students or change any room/application status.

## Notification behavior and limits
- The existing `notifications` table and account realtime listener are preserved. New **idempotent private admin rows** are generated by triggers on new applications, reservations, single-room requests, and inbound enquiry messages. These do not send emails or WhatsApps and do not obstruct submissions if alert recording fails.
- The global signed-in notification bridge listens even while viewing public or admin pages. Account toasts use privacy-safe generic copy and open the appropriate admin workspace. AdminOS **Technology → Notifications & Sounds** and student **My Updates** expose per-type tone settings.
- Sound is **off by default**, opt-in and local to the device, with Gentle/Chime/Bright/Urgent/Silent previews for applications, reservations, enquiries and general events. JavaScript tones work only while the tab is open/foreground and browser/device permits sound.
- Browser/web-push requires explicit permission from a user gesture, supported browser or installed PWA, a current Workbox worker, available VAPID key, successful PushManager subscription, and a saved endpoint on `push_subscriptions`. New **status** operation in the authenticated push-subscription Edge Function verifies that server persistence actually succeeded. It never claims browser grant = backend subscription = delivered message.
- At audit time there were **zero web-push subscriptions** and no automatic `notifications`→`send-push` dispatcher. Therefore closing a browser cannot currently be guaranteed to show new notifications. A future separate server dispatch and end-to-end push test is required for dependable closed-app web delivery; browser/OS may delay, silence or block delivery. The Android native notification system has separate provider/fallback behavior and is unchanged.
- Anonymous browsers are not subscribed to personalized account notifications and cannot receive private student data. They may see only general site promotional announcements while browsing.
