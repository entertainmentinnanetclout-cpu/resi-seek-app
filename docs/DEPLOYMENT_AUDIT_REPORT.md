# Deployment Audit Report

## Verdict

Preview and Production are the same build, both pointing at the External Supabase project. The reported "preview vs production drift" is not a frontend deployment problem — it is a **schema-delivery gap** between the two databases the workspace touches.

## Environments

| Concern | Preview | Production |
|---|---|---|
| Build pipeline | Lovable Vite build | Same build, promoted |
| Frontend bundle | `id-preview--dedebc2a-aca6-4fe3-8e88-445bf6af16bd.lovable.app` | `reskonnect.lovable.app` |
| `VITE_SUPABASE_URL` | `https://mefjzkhobkltlbmhusdh.supabase.co` | same |
| `VITE_SUPABASE_ANON_KEY` | External anon | same |
| Edge functions runtime | External (via `EXTERNAL_SUPABASE_*` secrets) | same |
| `VITE_BACKEND_PROVIDER` | unset → defaults to `supabase` driver | same |

No environment mismatch. No stale build. No leftover Lovable Cloud frontend wiring.

## Where the drift actually is

```text
Frontend  + Edge functions   ──►  External Supabase  mefjzkhobkltlbmhusdh  (LIVE DATA)
supabase--migration tool     ──►  Lovable Cloud      vmqqkebojldjsyxcewdb  (mirror)
```

`supabase/config.toml` pins `project_id = vmqqkebojldjsyxcewdb`, so every migration we have run lands in the Lovable mirror only. External production has never received any of:

- Find My Res V3.0 columns on `residences` (`category`, `gender`, `is_tut_accredited`, `is_furnished`, `has_wifi`, `has_parking`, `slug`, …)
- `slug` auto-generation trigger
- `filter_config` table + seeds
- `sync_queue`, `health_status`
- Marketplace `enforce_marketplace_order_seller()` trigger
- `residences.contact_email` / `contact_phone` column-level REVOKE
- Tightened RLS policies replacing `WITH CHECK (true)`
- Handover Pack integrity view + `validate_handover_pack()`

`src/integrations/supabase/types.ts` was hand-edited to reflect the Lovable mirror schema, so the build stays green even though the External database is missing these objects.

## Fix (operator action required)

1. Open the External Supabase SQL Editor (project `mefjzkhobkltlbmhusdh`).
2. Paste and run `docs/EXTERNAL_PARITY_CATCHUP.sql` (idempotent, rerunnable, non-destructive).
3. Run the verification queries at the bottom of that file. All should return non-empty results.
4. Reload the public site. No frontend redeploy is required — the bundle is unchanged.
5. From an admin account, open Operations Hub → Applications and click "Run Pre-Export Validation". A green banner confirms `validate_handover_pack` is live in External.

## Going forward

Until the workspace is repointed at External via the Supabase Lovable connector, every new migration generated by the assistant lands in the Lovable mirror. Ship each new migration as an entry in a follow-on `EXTERNAL_PARITY_*.sql` file so the operator can replay it into External in the same session.
